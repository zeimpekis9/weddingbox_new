# Database and media cutover plan

The offline gate is `node scripts/migration/reconcile.mjs <source-manifest.json> <target-manifest.json>`. Each manifest contains an `events` array of event UUIDs and a `records` array. Records contain `id`, `eventId`, `type` and a SHA-256 of canonical metadata in `metadataSha256`. Photo, video, voice and cover records also contain `bytes` and `originalSha256`. The target includes its event-scoped original `key`. Generate both hashes independently from the source and destination bytes and keep manifests in restricted storage. The command reports aggregate mismatches and exits nonzero for discrepancies.

The synthetic gate verifies matching manifests, missing records, metadata and content mismatches, and cross-event keys. The live inventory retry still failed DNS resolution. No live data import, production switch, or Supabase retirement has been executed.

## Legacy mapping to the local foundation

Keep source UUIDs for events, settings and submissions. Preserve timestamps, text, guest names, branding and tab configuration. Validate legacy slugs against the target check and retain a redirect mapping if any change is approved. Reconcile null dates, timestamps, approval flags and settings before mapping; keep an exception journal rather than silently applying target defaults to existing values. Convert approved=true to approved and false to pending. Quarantine unknown approval states until reviewed. Map media URL or embedded data bytes to future event-owned media rows after validated copy; the foundation submission table intentionally has no storage URL column. Treat the cover URL column as a compatibility field until cover references migrate to media IDs. Provision event memberships only from an operator-approved owner mapping. No production rows or bytes were transferred in this phase.

## Inventory and rehearsal

1. Establish who can authorize and run read-only source exports. Capture PostgreSQL version, catalog inventory, deployed application version and actual write channels (including direct browser writes and scheduled jobs). Export only allowed application tables with a consistent snapshot using an approved direct connection; keep encrypted read-only copies and source schema fingerprint. Export inventory and bytes of every applicable bucket independently. Supabase DB backup excludes object bytes. [Supabase backup](https://supabase.com/docs/guides/platform/backups)
2. Stage using isolated target PostgreSQL and R2. Use deterministic idempotent mapping by legacy source ID/key and a durable migration journal recording outcome, byte count, SHA-256 and target reference. Re-run against a changed source to prove updates, deletes, replaced covers and status changes reconcile. Snapshot dry runs use restricted production data only where approved.
3. Preserve event, settings and submission IDs, timestamps, Unicode and source approval state. Report duplicate settings, ambiguous slugs, nullable FKs, malformed flags and missing objects for disposition. Never silently coerce an approved unknown to public. Provision two verified owners with new credentials/MFA and explicit membership. Import no Supabase Auth system tables, sessions, JWT signing keys, RLS grants or Storage internals.
4. Classify object references by cover/photo/video/voice and resolve only expected provider host/bucket/key. Verify event UUID prefix matches owning row. Never fetch an arbitrary URL. Decode bounded data URLs, preserve bytes and inspect format. Stream copy and hash each source and destination; keep retry journal, quarantine broken/conflicting references, and inventory unreferenced bytes separately. Avoid resurrecting possibly deleted content without a documented owner decision.
5. Reconcile counts by event/type/moderation, canonical data hashes (with documented field mapping), blob byte counts and SHA-256, absent/extra rows and objects, valid covers, membership and guestbook visibility. Run import twice to prove identical logical results. All expected objects must match, with every exception acknowledged and documented before cutover.

## Cutover and rollback

- Seed/copy before change window. Freeze writes at the legacy database/storage boundary including direct Supabase clients and dashboards, preserving reads where appropriate. Verify freeze with controlled write probes, then take a consistent final metadata snapshot and object delta. Compare final source inventory against target, reconcile deletes and replacements, and keep an encrypted source snapshot. No dual writes by default. Prestage QR, owner recovery and DNS with the planned window and perform a rehearsal using separate domains.
- Gate public switch on matching manifests, authorized and unauthorized test cases, verified receipt, tested backups, supported build, and approved downtime. While public target writes remain disabled, smoke-test using isolated synthetic records, then flip traffic, smoke-test QR and MFA, and deliberately enable real target writes. Record cutover timestamp and save journal watermark.
- **Before first target write**, switch traffic back and re-enable the approved legacy write boundary after confirming legacy consistency. **After first target write**, stop admissions if needed, keep in-flight objects and capture DB/R2 delta plus journal; forward repair is the default. Roll back to the old stack only if reverse import of new/edited metadata, originals and deletions has been implemented, verified and authorized, or an approved recovery bridge preserves them without reopening unsafe access. A DNS flip alone can strand accepted uploads. Pause, reconcile all issued receipts and test again before resuming.
- Observe through an agreed window with encrypted restricted source retention, public sharing disabled as appropriate, and no active runtime dependence. Separate decommission approval after reconciliation, restored backup and retention review. Do not destroy the only verified copy.
